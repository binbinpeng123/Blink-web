## 4. 压测方法

执行命令：

```bash
BLINK_ACCESS_KEY=<假凭据> BLINK_SECRET_KEY=<假凭据> \
  npm run bench -- --spawn \
    --bin ../Blink/bin/blink \
    --sizes 64KiB,1MiB,8MiB,32MiB \
    --concurrency 1,4,16 \
    --max-write-mib 512
```

口径：

- **`--spawn`**：每个尺寸启动一个独占的临时 Blink 实例与临时数据目录，结束后删除
  目录；避免不同尺寸的数据互相占用磁盘，也避免长期实例的缓存偏差。
- **样本**：每用例最多 1000 个，测量时长上限 30 s，先完成一个完整并发波次再检查
  停止条件，因此时长受限的用例样本数可能少于 1000。
- **warmup**：目标的 10%，不计入指标。
- **唯一数据**：每个样本正文由会话盐 + 序号 + xorshift 生成，避免 Blink 内容寻址
  去重把实际写入量压小。
- **校验和**：PUT 校验响应中的 SHA-256；GET 校验正文 SHA-256。本次
  `checksumMismatches = 0`。
- **重试**：默认关闭，错误直接计入 `errors`。
- **写入预算**：整次运行 512 MiB，按 4 个尺寸均分，每个尺寸 128 MiB；预算在发请求
  前扣减，失败请求也计入。GET 不扣写入预算。
- **清理**：每个尺寸结束后删除临时后端与数据目录；运行前磁盘可用 3,435,282,432 B，
  运行后 3,428,524,032 B，差 6.4 MiB，未留下临时目录。

原始结果：`bench-results/bench-20261025-184159.json`（`bench-results/` 已 gitignore）。

### 5.3 `budgetLimited` 的口径

- PUT：用例的 `sampleTarget` 因写入预算被下调，或预算已不足以执行。样本数为 0 的
  用例没有 p50/p95/p99。
- GET：数据集准备没有达到期望数量（`max(4, concurrency × 2)`）时也会标记
  `budgetLimited`。这不等于测量失败：8 MiB × 16 用 16 个对象完成了 1000 个样本。
- 32 MiB 的三个 GET 用例样本少于 1000，是 30 s 时长上限先到，不是预算问题。

## 6. 结果解读

- **小对象 PUT 受 `fsync always` 支配**：64 KiB 并发 1 的 p50 为 24.8 ms、吞吐
  2.5 MiB/s；并发 4 吞吐只升到 4.3 MiB/s，且 p50 升到 58 ms。这是每请求同步落盘
  的排队效应，不是客户端并发能力不足。换 `--fsync-policy meta` 会得到完全不同的
  数字，不能与本次表格混比。
- **GET 随并发接近线性上升，随后饱和**：64 KiB 从 21 MiB/s 升到 186 MiB/s，1 MiB
  从 158 MiB/s 升到 497 MiB/s，8 MiB 在并发 16 达到约 507 MiB/s 后不再明显增长。
  32 MiB 在并发 16 的 p99 为 1.79 s，吞吐反而略低于并发 4（476 vs 510 MiB/s），
  说明已超过本机回环的舒适区间。
- **大对象 PUT 的样本太少**：8 MiB 只有 15 个样本、32 MiB 只有 3 个，百分位数基本
  没有统计意义，只能说明单请求量级（p50 约 108 ms / 418 ms）。要比较多并发大对象
  写入，需要提高预算或在足够大的空闲磁盘上重跑。
- **本次零错误、零校验和不一致**：所有成功响应的 SHA-256 都与客户端计算值一致，
  没有出现传输截断或内容替换。
- **运行成本**：整轮 247.5 s，写入正好 512 MiB（4 × 128 MiB），临时目录全部清理。

## 7. 浏览器面板

- 默认总写入预算 256 MiB，按尺寸均分；受浏览器 HTTP/1.1 每源约 6 连接与全局
  `Semaphore(4)` 限制。
- e2e 中用 64 KiB、并发 1、5 个样本、时长 0 做冒烟：两行结果均 `ok`，导出 JSON
  可用，清理后桶为空。
- 面板数字只用于确认链路与回归趋势，**不能代表服务端吞吐**；权威基线以本文第 5
  节的 CLI 结果为准。

  开发机 `/tmp` 约 43 GiB，已足够支撑更大的预算。

## 10. 公网实测（临时隧道 + 令牌登录）

2026-10-26 在真实公网链路上做了一次端到端冒烟，验证「公网访问 + 令牌门禁 + 签名
穿透代理」这条组合能工作。**这一节只回答"能不能用"，不提供性能结论。**

### 10.1 拓扑与条件

```
浏览器 (公网)
  └─ HTTPS ─► Cloudflare 临时隧道 (quick tunnel, https://*.trycloudflare.com)
                └─► 本机 127.0.0.1:8080  Blink-web 生产服务器（令牌模式）
                      └─► /s3 代理（保留 Host，剥离会话 Cookie）
                            └─► 127.0.0.1:9000  逐连接 SSH 中继
                                  └─► bd13 127.0.0.1:9000  Blink 后端
```

| 维度 | 值 |
| --- | --- |
| 入口 | Cloudflare quick tunnel（地址临时，进程/机器重启即失效） |
| 门禁 | `BLINK_WEB_TOKEN`（≥32 字符随机串）+ HMAC 签名 HttpOnly 会话 Cookie |
| 中继 | 本机 Python TCP 中继，每条连接独立 SSH，仅监听 `127.0.0.1` |
| 后端 | bd13 上 Blink `0.1.0-cors`，与第 9 节同一台机器 |
| 浏览器 | 无头 Chrome 155，Puppeteer 驱动 |
| 样本 | 1 个 12 MiB 对象，8 MiB 分片，随机内容 |

### 10.2 门禁与签名验证

| 检查 | 结果 |
| --- | --- |
| 匿名 `GET /`（`Accept: text/html`） | 303 → `/__login?next=%2F`，不触达后端 |
| 匿名 `GET /s3/<bucket>` | 401，`application/xml`，`<Code>AccessDenied</Code>` |
| 匿名 `HEAD /s3/<bucket>/<key>` | 401，无正文 |
| `/__authz` 匿名 | `{"required":true}` |
| 错误令牌 | 303 → `/__login?error=1`，不下发 Cookie |
| 正确令牌（经 HTTPS） | 303 → `/`，Cookie 带 `HttpOnly; SameSite=Lax; Secure`，响应带 HSTS |
| 签名 `ListBuckets` 经隧道 | 成功，无 `SignatureDoesNotMatch`（代理保留了原始 `Host`） |
| 会话 Cookie 是否到达后端 | 否（代理剥离 `cookie` / `set-cookie`） |

### 10.3 上传 / 下载

| 方向 | 大小 | 耗时 | 吞吐 | 校验 |
| --- | --- | --- | --- | --- |
| 上传（8 MiB 分片） | 12 MiB | 39.2 s | ≈ 0.31 MiB/s | 每片 SHA-256 通过 |
| 下载（Range 分块） | 12 MiB | 28.2 s | ≈ 0.43 MiB/s | 下载文件 SHA-256 与源文件一致 |

吞吐只有 ~0.3 MiB/s，瓶颈在「公网 → Cloudflare → 本机 → 逐连接 SSH → bd13」
这条五段链路：每条 TCP 连接都新建一次 SSH 会话，且公网 RTT 全程叠加。**不要把
这个数字当作 Blink 或 Blink-web 的吞吐能力**；服务端基线见第 9 节（同机自环，
GET 峰值约 699 MiB/s）。

### 10.4 过程中发现并修复的问题

- **登录后仍 401**：`FetchTransport` 原用 `credentials: 'omit'`，浏览器 fetch
  `/s3` 不带会话 Cookie，门禁永远判定未登录。改为 `same-origin` 后修复；跨源端点
  仍不会收到凭据，压测 CLI（Node 无 Cookie 罐）行为不变。
- **401 被显示成 `UnknownError`**：未登录时 `/s3` 返回纯文本 401，前端按 S3 协议
  解析 XML 失败。改为返回 `AccessDenied` XML（`HEAD` 无正文）。
- **Cloudflare → 中继直连 POST 挂起**：隧道直接指向 5173 中的中继时，`POST /__login`
  120 s 无响应（cloudflared 记录 `context canceled`），判断为 h2c 与逐连接中继的
  组合问题。改为隧道指向本机生产服务器、只有 `/s3` 走中继后正常。

### 10.5 复现方式

令牌模式启动（令牌只从环境变量读，不落盘、不写日志）：

```bash
# 1. 后端（任意可达地址，这里经中继）
# 2. 前端生产服务器（必须显式提供 ≥32 字符令牌）
BLINK_WEB_TOKEN="$(openssl rand -base64 32)" \
BLINK_ENDPOINT=http://127.0.0.1:9000 \
HOST=127.0.0.1 PORT=8080 node server/server.ts

# 3. 临时公网入口
cloudflared tunnel --url http://127.0.0.1:8080
```

用隧道输出的 `https://*.trycloudflare.com` 打开即可看到登录页；会话默认 24 h，
换令牌后所有旧 Cookie 立即失效。隧道地址是临时的，**不要把它当稳定入口**，生产
应使用命名隧道或自己的 TLS 反向代理，且反向代理必须保留原始 `Host`。
